Great. Now, what database should I use to store tokens and sessions?

[TURN 2 — ASSISTANT]
For token storage in a microservices auth system, I recommend Redis with appropriate TTLs for active sessions and refresh tokens. This gives you:
- Sub-millisecond token lookup
- Automatic expiry via Redis TTL (no garbage collection needed)
- Horizontal scaling with Redis Cluster

For audit logs and long-term token records, use PostgreSQL. Store a hash of the token (SHA-256), not the raw token, to prevent exposure if the database is compromised.

Schema considerations:
- tokens(token_hash, user_id, scope, issued_at, expires_at, revoked)
- sessions(session_id, user_id, device_fingerprint, created_at, last_seen)
- refresh_tokens(rt_hash, access_token_hash, user_id, family, rotation_count)

[TURN 3 — USER]
Can you also explain token rotation and refresh token family tracking?

[TURN 3 — ASSISTANT]
Token rotation is the practice of issuing a new refresh token each time the old one is used. This limits the window an attacker has to use a stolen refresh token.

Refresh token family tracking detects token reuse attacks. Each refresh token belongs to a "family" (a lineage starting from the original login). When a refresh token is used:
1. A new refresh token is issued (same family, incremented rotation_count)
2. The old refresh token is marked as consumed
3. If an already-consumed token from the same family is presented, the entire family is revoked

This detects token theft because an attacker who stole a refresh token and used it first would cause the legitimate user's subsequent request (with the now-invalidated old token) to trigger family revocation, ending both sessions.

[TURN 4 — USER]
How do I handle token revocation in distributed systems?

[TURN 4 — ASSISTANT]
Token revocation in distributed systems is tricky because access tokens are stateless (JWT) and each service validates them independently without a central lookup.

The main approaches:

**Short-lived JWTs + blocklist**: Issue JWTs with 5-15 minute expiry. Keep a revocation blocklist in Redis. Each service checks the blocklist on every request. The blocklist only needs to hold tokens until they expire naturally.

**Token introspection**: All services make a real-time call to the authorization server to validate each token. Simple but adds latency and creates a single point of failure. Use with caching and circuit breakers.

**Push invalidation**: The auth server pushes revocation events via message queue (Kafka, Redis Pub/Sub). Services maintain local revocation caches. Eventual consistency — there's a window where a revoked token may still be accepted.

For most production systems: short-lived JWTs (15 min) + Redis blocklist for critical revocations (compromised accounts, admin actions) + refresh token rotation is the right balance.

[TURN 5 — USER]
What rate limits should I set on the token endpoint?

[TURN 5 — ASSISTANT]
Token endpoint rate limits should be aggressive because brute-force attacks on this endpoint are the primary credential stuffing vector.

Recommended limits:
- Per-IP: 10 requests/minute for /oauth/token (hard limit, 429 with Retry-After)
- Per-user: 5 failed attempts/15 minutes triggers account lockout (soft lock requiring email verification)
- Per-client: 1000 requests/minute for trusted first-party mobile apps, 100/minute for third-party

Implementation notes:
- Use sliding window counters in Redis (not fixed window to prevent burst attacks at window boundaries)
- Log all rate-limited attempts with source IP, client_id, and timestamp for forensics
- Exempt health-check endpoints from rate limiting
- Consider CAPTCHA or device fingerprinting after 3 failed attempts from same IP

[TURN 6 — USER]
Can you show me a complete OAuth2 server implementation in Python using FastAPI?

[TURN 6 — ASSISTANT]
Here is a minimal but production-oriented OAuth2 authorization server using FastAPI and python-jose for JWT handling:

```python
from fastapi import FastAPI, HTTPException, Depends, Request
from fastapi.security import OAuth2PasswordBearer, HTTPBearer
from pydantic import BaseModel
from datetime import datetime, timedelta
import hashlib, secrets, redis, jwt
from typing import Optional

app = FastAPI()
r = redis.Redis(host="localhost", port=6379, db=0)

SECRET_KEY = "replace-with-env-var-in-production"
ALGORITHM = "HS256"
ACCESS_TOKEN_EXPIRE_MINUTES = 15
REFRESH_TOKEN_EXPIRE_DAYS = 30

class TokenRequest(BaseModel):
    grant_type: str
    username: Optional[str] = None
    password: Optional[str] = None
    refresh_token: Optional[str] = None
    code_verifier: Optional[str] = None

def create_access_token(user_id: str, scope: str) -> str:
    payload = {
        "sub": user_id,
        "scope": scope,
        "exp": datetime.utcnow() + timedelta(minutes=ACCESS_TOKEN_EXPIRE_MINUTES),
        "iat": datetime.utcnow(),
        "jti": secrets.token_hex(16),
    }
    return jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM)

def verify_token(token: str) -> dict:
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        token_hash = hashlib.sha256(token.encode()).hexdigest()
        if r.get(f"revoked:{token_hash}"):
            raise HTTPException(status_code=401, detail="Token revoked")
        return payload
    except jwt.ExpiredSignatureError:
        raise HTTPException(status_code=401, detail="Token expired")
    except jwt.InvalidTokenError:
        raise HTTPException(status_code=401, detail="Invalid token")

@app.post("/oauth/token")
async def token_endpoint(request: Request, body: TokenRequest):
    client_ip = request.client.host
    rate_key = f"rate:{client_ip}"
    count = r.incr(rate_key)
    if count == 1:
        r.expire(rate_key, 60)
    if count > 10:
        raise HTTPException(status_code=429, detail="Rate limit exceeded")
    # ... (grant type handling omitted for brevity)
```

This covers the core structure. For production, add: proper user database lookup, bcrypt password verification, PKCE validation, and refresh token family tracking as discussed earlier.

[TURN 7 — USER]
Thanks. One more thing — what logging should the auth server emit?

[TURN 7 — ASSISTANT]
Auth server logging is critical for security monitoring. Every token issuance, validation failure, and revocation event should be logged with enough detail to reconstruct an incident.

Minimum required events:
- token_issued: {user_id, client_id, scope, issued_at, token_jti, source_ip}
- token_validated: {token_jti, service_id, validated_at, result: ok|revoked|expired}
- token_revoked: {token_jti, reason, revoked_by, revoked_at}
- login_failed: {username_hash, client_id, failure_reason, source_ip, timestamp}
- rate_limit_hit: {source_ip, client_id, endpoint, count, timestamp}
- refresh_token_reuse_detected: {family_id, user_id, revoked_token_hash, source_ip}

Log format: structured JSON, one event per line, sent to a centralized log aggregator (e.g., OpenSearch, Splunk). Do NOT log raw token values — always log SHA-256 hashes of tokens. Set log retention per your compliance requirements (typical: 90 days hot, 1 year cold).
